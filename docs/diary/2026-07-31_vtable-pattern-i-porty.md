# 2026-07-31 — vtable-паттерн и порты

- Закрепили `pub fn`: `pub` делает декларацию (функцию, `const`, `var`,
  `struct`) видимой за пределами файла — файл в Zig и есть модуль/namespace,
  без `pub` декларация приватна для него. Доступ снаружи — только через
  `@import("файл.zig").имя`.
- В Zig нет классов и наследования, поэтому абстракции строятся одним из
  двух путей, и выбор зависит от того, закрыт или открыт набор реализаций:
  - **Comptime-generics** (`anytype` + структурная типизация, проверяется
    компилятором по месту вызова, резолвится и мономорфизируется на этапе
    компиляции, без рантайм-оверхеда) — когда все варианты типа известны
    заранее.
  - **Vtable-паттерн** (структура из `ptr: *anyopaque` + таблица указателей
    на функции) — когда набор реализаций открыт и определяется в рантайме
    (кто-то извне подключает свою реализацию). Это идиоматичный, а не
    самодельный подход — так устроены `std.mem.Allocator`, `std.io.Writer`/
    `Reader`, `std.Random` в стандартной библиотеке. Важный нюанс философии
    Zig: vtable — это инструмент под конкретную задачу (рантайм-полиморфизм),
    а не дефолтный выбор; там, где хватает comptime-generics, они дешевле
    и проще.
- Разобрали на конкретном примере — `MoveWindowUseCase` из `draft.ts`
  (use case, принимающий `WindowManagerPort` через конструктор). Это ровно
  случай открытого набора реализаций (Sway/Hyprland/мок для тестов), то есть
  кандидат на vtable. Соответствие с TS:
  - порт (`WindowManagerPort`, интерфейс) → структура
    `{ ptr: *anyopaque, moveFn: *const fn (*anyopaque, Direction) void }` с
    методом `move`, который дергает `moveFn` через сохранённый `ptr`;
  - use case (`constructor(private windowManager)` + `execute`) → структура
    `MoveWindowUseCase` с полем `window_manager: WindowManagerPort` и методом
    `execute`, который делегирует вызов в порт — прямой аналог TS-версии;
  - конкретная реализация (`class SwayWindowManager implements ...`) →
    отдельная структура + функция-метод `port()`, которая упаковывает себя
    в `WindowManagerPort` (сохраняет `self` как `ptr`, передаёт указатель на
    свою `moveImpl`).
  - единственное действительно новое место — `@ptrCast`/`@alignCast` внутри
    `moveImpl`, где `*anyopaque` приводится обратно к конкретному типу
    реализации.
- Разобрали `struct` вопрос "чем принципиально отличается от класса", по
  пунктам:
  - `struct` — это только разметка данных + namespace для функций, никакой
    скрытой машинерии сверху (в отличие от класса в TS/JS с рантайм-
    поддержкой наследования/диспетчеризации).
  - Нет наследования и нет виртуального диспетчеринга как языковой фичи —
    именно поэтому vtable в `WindowManagerPort` пришлось строить руками:
    в TS это делает рантайм автоматически, в Zig это ручная работа
    программиста.
  - `self` — не спец-сущность языка, а обычный первый параметр функции;
    `self.move(x)` — синтаксический сахар ("если тип первого параметра
    функции совпадает с типом слева от точки — можно звать как метод").
  - Нет конструктора/деструктора как языковой фичи — `init`/`deinit` чистая
    конвенция, компилятору о них ничего не известно.
  - Приватность в Zig гранулируется по **файлу**, а не по типу: `pub`
    перед декларацией внутри `struct` управляет видимостью за пределами
    файла. Функция без `pub` внутри структуры недоступна из других файлов,
    но доступна из любого кода в том же файле (в т.ч. из других структур
    этого файла) — это грубее, чем `private` в TS-классе.
- Разбор `WindowManagerPort` построчно, с двумя важными коррекциями
  предыдущих объяснений:
  - `const WindowManagerPort = struct {...}` без `pub` — ничего на экспорт
    не идёт; экспорт решает исключительно наличие/отсутствие слова `pub`
    прямо перед `const`, никакой другой логики компилятор не применяет.
  - `anyopaque` — это **не** аналог `any` из TS (там "выключить проверку
    типов вообще"). С `*anyopaque` нельзя сделать ничего, кроме передачи
    дальше и явного `@ptrCast` к конкретному названному типу — точнее
    аналогия из TS: `unknown`, а не `any`.
  - Согласованность реализации с портом всё-таки проверяется компилятором,
    но в одном конкретном месте — в конструкторе конкретной реализации
    (`fn port(self: *SwayWindowManager) WindowManagerPort`), где сигнатура
    `moveImpl` строго сверяется с типом поля `moveFn`. Не проверяется
    компилятором только связка внутри `moveImpl`: что `ptr`, пришедший в
    рантайме, действительно указывает на `SwayWindowManager` — это
    единственный "шов", где корректность держится на дисциплине
    программиста (единственное место, создающее `WindowManagerPort`, —
    сам `port()`, и там `ptr`/`moveFn` всегда берутся из одного `self`),
    а не на проверке типов.

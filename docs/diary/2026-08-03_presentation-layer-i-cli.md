# 2026-08-03 — presentation-слой, composition root и первый cli-баг

- Обсудили порядок работы: вместо того чтобы сразу писать реальный
  sway-адаптер, решили сначала собрать cli с заглушкой (вывод в терминал
  вместо настоящего sway IPC) — чтобы прогнать всю цепочку
  `main → cli → use-case → port → adapter` целиком, дёшево поймать ошибки
  сборки/API, и только потом подставить настоящий адаптер за тот же порт.
- Разобрали вопрос "cli — это infrastructure или нет". Вывод: нет,
  это отдельный presentation-слой. В терминах портов-и-адаптеров это два
  разных направления:
  - **sway-adapter** — *driven*-адаптер: application стучится в него через
    порт наружу;
  - **cli** — *driving*-адаптер: сам дёргает use-case снаружи, ничего не
    реализует.
  Свалить их в один узел `infrastructure` (как было раньше) смазывало это
  различие и было ровно тем незакрытым пунктом из `docs/planning.md` про
  разрыв инверсии зависимостей. Поправили `docs/diagram.d2`:
  `presentation.cli` → `application.use-cases`, `infrastructure.adapters.sway`
  → `application.ports`, прямой связи presentation → infrastructure нет.
- Разобрали, почему presentation вызывает use-case напрямую, а не через
  абстракцию: `MoveWindowUseCase` — не интерфейс, у него нет второй
  реализации, абстрагировать нечего (в отличие от `Port`, у которого
  реализаций много и они подставляются в рантайме). Единственное место,
  где нужна подстановка конкретной реализации порта — **composition root**
  (`main.zig`): он один знает про все слои сразу, собирает конкретный
  адаптер, заворачивает в `Port`, создаёт готовый `MoveWindowUseCase` и
  отдаёт его в presentation уже собранным. Presentation получает готовый
  use-case и просто вызывает `.execute()`.
- Написали `MoveWindowCli` (`src/presentation/cli/move-window.cli.zig`).
  В первой версии — баг: `self.move_window_use_case(.left)` пытался
  вызвать поле-структуру как функцию. Разобрали механизм метод-вызова
  через точку подробно: `x.foo(args)` — компилятор переписывает это в
  `T.foo(x, args)`, если `foo` объявлена **внутри namespace типа `T`** и
  её первый параметр имеет тип `T`/`*T`/`*const T`. `execute` — обычная
  функция с двумя параметрами (`self`, `direction`), сахар просто прячет
  подстановку первого. Поправили на `self.move_window_use_case.execute(.left)`.
- Разобрали мелкую стилистическую коллизию: поле `move_window_use_case`
  и импортированный модуль назывались одинаково. Прикинули альтернативы —
  укоротить поле до `use_case`, переименовать импорт, или назвать по роли
  (`interactor`, термин из Clean Architecture). Выбрали переименование
  импорта (`use_case = @import(...)`), поле осталось разворачивающим.
  Отметили, что это расходится с конвенцией остальных файлов проекта
  (`window_manager_port`, `move_window_use_case` — полные имена при
  импорте) — не баг, но стоит на будущее выбрать один подход.
- Добавили `right()` симметрично `left()` — оба варианта `Direction`
  теперь покрыты. TODO про обработку ошибок в `execute` оставили как
  есть: пока преждевременный, `Port.move()`/`move_fn` возвращают `void`,
  ловить нечего до того момента, как порт начнёт возвращать `!void`.

## На завтра

Собрать саму заглушку — конкретную реализацию `Port`, которая печатает
направление в терминал вместо реального IPC, и написать composition root
в `main.zig`: создать заглушку, обернуть в `Port`, собрать
`MoveWindowUseCase`, передать в `MoveWindowCli`, вызвать `left`/`right`.
Только после того как вся цепочка реально прогонится и что-то напечатает —
переходить к настоящему sway-адаптеру (`src/infrastructure/adapters/sway.adapter.zig`,
сейчас пустой).

# 2026-08-07 — Справка по i3-ipc протоколу (для фрейминга + юнит-теста)

Разобрали формат i3-ipc перед тем, как писать encode/decode в
`sway.adapter.zig`. Ниже — справочная информация без кода, чтобы начать
следующую сессию сразу с реализации.

## Формат сообщения

Каждое сообщение (запрос, ответ, событие) — заголовок фиксированной длины
14 байт, за которым идёт JSON-пейлоад:

| Смещение     | Размер      | Поле    | Содержимое                                               |
| ------------ | ----------- | ------- | -------------------------------------------------------- |
| 0–5          | 6 байт      | magic   | ASCII-строка `i3-ipc`, **без** нуль-терминатора          |
| 6–9          | 4 байта     | length  | `u32`, длина пейлоада в байтах (не считая заголовок)     |
| 10–13        | 4 байта     | type    | `u32`, тип сообщения                                     |
| 14…14+length | length байт | payload | UTF-8 JSON, без нуль-терминатора и без завершающего `\n` |

Endianness: спецификация формально не фиксирует порядок байт для
`length`/`type` — исторически native byte order, потому что это
внутримашинный IPC. На x86_64/aarch64 это little-endian. Не "гарантия
протокола", а бытовой факт — для личного десктопного инструмента можно
закладываться на native.

## Типы сообщений (запросы)

```
0  RUN_COMMAND       payload: сырая командная строка ("move left"), НЕ JSON
1  GET_WORKSPACES
2  SUBSCRIBE         payload: JSON-массив имён событий, например ["window","workspace"]
3  GET_OUTPUTS
4  GET_TREE
5  GET_MARKS
6  GET_BAR_CONFIG
7  GET_VERSION
8  GET_BINDING_MODES
9  GET_CONFIG
10 SEND_TICK
11 SYNC
12 GET_BINDING_STATE
```

У sway есть свои расширения (`GET_INPUTS`=100, `GET_SEATS`=101 и т.д.), но
для move-window они не нужны.

Важный нюанс: пейлоад **запроса** `RUN_COMMAND` — это не JSON, это голая
строка команды. А пейлоад **ответа** на него — JSON-массив объектов
`{"success": bool, "error": string|null}` (по одному на каждую подкоманду,
если их несколько через `;`). Запрос и ответ на один и тот же `type`
кодируются по-разному — частый источник багов.

## События (после SUBSCRIBE)

После подписки в тот же сокет асинхронно прилетают события — тот же
14-байтовый заголовок, но `type` со старшим битом:

```
event_type = 0x80000000 | index
```

где index: `0 workspace, 1 output, 2 mode, 3 window, 4 barconfig_update,
5 binding, 6 shutdown, 7 tick, ...`

При разборе заголовка: `type & 0x80000000 != 0` → это событие, не ответ на
запрос. Не нужно сегодня (SUBSCRIBE — шаг после базового
RUN_COMMAND/GET_TREE), но decode стоит сразу закладывать с этим различением,
чтобы не переписывать потом.

## Конкретный пример байтов (фикстура для юнит-теста encode)

Запрос `RUN_COMMAND` с командой `"move left"` (9 байт):

```
"i3-ipc"                    — 6 байт magic
09 00 00 00  (u32 LE = 9)   — 4 байта length
00 00 00 00  (u32 LE = 0)   — 4 байта type (RUN_COMMAND)
"move left"                 — 9 байт payload
```

Итого 14 + 9 = 23 байта. Готовый кейс: собрал функцией encode — сравнил
байт-в-байт с этим массивом.

## Кейсы для теста decode

- Ответ на `GET_VERSION` (type=7) — простой стабильный JSON
  (`{"major":1,"minor":...,"human_readable":"...",...}`).
- Запрос/ответ с пустым пейлоадом (например `GET_TREE`, type=4, length=0) —
  проверить, что decode не падает на нулевой длине.
- Заголовок со старшим битом type (например `0x80000003` — событие
  `window`) — проверить, что decode отличает событие от ответа, даже если
  разбор самого пейлоада события ещё не реализован.

## Как добыть реальные байты для фикстур (не выдумывать по спеке)

Подслушать трафик nested-сессии:

```
socat -x UNIX-CONNECT:$SWAYSOCK -
```

запустить, и в соседнем терминале дать `swaymsg -t get_version` — hex-дамп
обеих сторон обмена, реальные байты можно скопировать в тест как
integration-фикстуру отдельно от синтетических кейсов выше.

## Как достать `$SWAYSOCK` вложенной (nested) сессии снаружи

Вложенная sway ставит `SWAYSOCK` только в своё окружение и окружение своих
детей — внешний терминал, из которого её запустили, эту переменную
автоматически не увидит:

```
WLR_BACKENDS=wayland sway &
cat /proc/$!/environ | tr '\0' '\n' | grep SWAYSOCK
```

(`$!` — PID только что запущенного фонового процесса). Либо: открыть
`foot`-терминал изнутри вложенной сессии (её собственными биндингами) и там
`echo $SWAYSOCK` — унаследует от родителя.

## Что НЕ входит в слой encode/decode

Чтение из сокета в реальности приходит частями (`read()` может вернуть
меньше байт, чем просили) — обработка partial reads (луп "читай пока не
наберёшь length") это уже слой сокет-I/O, не encode/decode. Юнит-тест
framing-функций работает над готовым `[]const u8` буфером в памяти, без
реального сокета.

# 2026-09-01 — Allocator: владение и подъём аллокации в родителя; типы литералов `.{ }`

Продолжение серии после 08-31 (`docs/diary/2026-08-31_stream-io-tipy-i-socket-obertka.md`).
Сессия — вперёд по открытому вопросу "буфер под `body_bytes`": разобрали `Allocator` с нуля
(владение, время жизни, откуда брать), плюс попутно синтаксис `.{ }`-литералов и модель чтения
из сокета (pull vs push). Решение по буферу принято — **Allocator**, не фиксированный буфер.

## Решение: буфер под `body_bytes` — Allocator

Из развилки 08-30/08-31 (Allocator vs фиксированный буфер) выбран **Allocator** — осознанно,
не по техническому превосходству варианта, а потому что пользователь хочет именно сейчас
руками пощупать ручное управление памятью (ключевая причина, а не "как правильнее для
`move`"). Живой экземпляр `std.mem.Allocator` берётся тем же путём, что и `io` — из
`init.gpa` в `std.process.Init` (см. 08-31 про `init.io`), протаскивается вниз по цепочке
аналогично.

## Ключевой вывод сессии: аллокацию можно (и нужно) поднять в `runCommand`

Разобрали "убегающую" аллокацию (память живёт дольше функции, которая её выделила) как
источник реальной сложности ручного управления памятью — в отличие от простого случая
alloc+`defer free` в одном скоупе, который пользователь самверно назвал "не такой уж и
сложный".

Пользователь сам пришёл к выводу и он **подтверждён как верный**: раз `runCommand` уже знает
`header_in.payload_length` до чтения тела (сначала читается и декодируется заголовок), можно
выделить `body_bytes` прямо в `runCommand`, а не внутри `readExact`:

```
const body_bytes = try allocator.alloc(u8, header_in.payload_length);
defer allocator.free(body_bytes);

try readInto(io, stream, body_bytes);   // не аллоцирует, просто заполняет чужой буфер
const result = try decodeReply(header_in, body_bytes);
```

Это схлопывает проблему владения обратно к простому случаю (alloc/free в одном скоупе) —
поднимать аллокацию наверх стоит именно тогда, когда размер известен заранее вызывающей
стороне (как здесь), а не как общее правило на все случаи.

**Важно для следующей сессии**: этот вывод сделан **после** того, как в код уже закоммичена
сигнатура `pub fn readExact(io, stream, allocator, bytes_length) ![]const u8` (со своим
`Allocator` внутри). По сегодняшнему выводу её, вероятно, стоит **пересмотреть** — заменить на
что-то вроде `readInto(io, stream, buffer: []u8) !void`, без `Allocator` внутри вообще, раз
аллокация переезжает в `runCommand`. Не сделано, это решение первым пунктом на старте.

## `Allocator` — что это и откуда берётся (спрашивали с нуля)

- `Allocator` — не память, а интерфейс/возможность её выделять; сама не имеет размера и не
  "бесконечна" — лимит определяет конкретная реализация за интерфейсом (`GeneralPurposeAllocator`
  — упирается в реальную RAM/своп, `FixedBufferAllocator` — в заданный буфер). `alloc()` всегда
  может провалиться (`error.OutOfMemory`) — это часть контракта, не крайний случай.
- Тип — `std.mem.Allocator`.
- Освобождать нужно **ровно** тот слайс, что вернул `alloc` (тот же указатель+длина) —
  освобождение другого — undefined behavior, debug-аллокаторы часто это ловят и паникуют.
- `defer` — не значение и не может быть "возвращён" из функции; в Zig нет замыканий (в отличие
  от JS/TS), так что паттерн "верни данные + cleanup-функцию" не переносится буквально. Ближайший
  Zig-идиоматичный аналог — структура со своим методом `deinit()`, которую зовёт вызывающая
  сторона сама, в своём скоупе (`ArrayList.deinit()`, `ArenaAllocator.deinit()`).

## Профилировка/дебаг памяти — на будущее, когда понадобится

`GeneralPurposeAllocator` — встроенная детекция утечек при `deinit()` (в debug-сборке умеет
показывать стектрейс места аллокации) — стартовая точка, ничего внешнего ставить не надо.
Дальше: `std.heap.LoggingAllocator` (лог каждого alloc/free), `valgrind --tool=memcheck`/`massif`,
`heaptrack`, ASan (`-fsanitize=address`) — не установлено, не нужно прямо сейчас.

## Побочные темы (закрыты, не требуют возврата)

- **`usize`** — беззнаковое целое размера указателя платформы (64 бита на этой машине), не
  "самое большое число" как концепция — просто разрядность, гарантированно достаточная для
  индексов/размеров в адресном пространстве. Прямой аналог — C `size_t`.
- **`.{ .field = value }`** — анонимный литерал, тип выводится через target-type inference не
  только из объявления переменной, но и из контекста параметра функции (пример из своего же
  кода: `execute(.left)` — `.left` выводится как `Direction.left` по типу параметра). Ведущая
  точка — общий механизм для enum-литералов (`.left`), struct/union-литералов (`.{ ... }`) и
  tuple/array-литералов (`.{ 1, 2, 3 }`), не только для struct.
- **`:` vs `=`** — `:` про тип (в объявлениях: переменная, поле структуры, параметр функции),
  `=` про значение (инициализация/литерал) — прямая параллель с TS (`let x: number = 5`).
- **Фрейминг/модель чтения** — уточнено: чтение из сокета не "сканирование в поисках magic",
  а pull-модель — `readExact` внутри `runCommand`/цикла событий сам блокирующе просит байты и
  ждёт, ОС будит поток когда данные готовы. Magic-строка — валидация уже прочитанного кадра, не
  механизм поиска его начала. `readExact` (цикл) нужен, потому что один `read()` может вернуть
  меньше байт, чем просили, даже на потоковом сокете.

# 2026-08-06 — Zig 0.16: новый Init.Minimal, *T vs *const T, первый рабочий `zig build run`

- Дособрали `main.zig` до конца — composition root теперь реально прогоняет
  `left`/`right` через весь стек (`main` → `RouterCli` → `MoveWindowCli` →
  `MoveWindowUseCase` → `WindowManagerPort` → `StubWindowManagerAdapter`).
  Проверено вживую:
  ```
  zig build run -- left   → stub adapter works with direction: left
  zig build run -- right  → stub adapter works with direction: right
  ```

- По дороге всплыло, что `std.process.args()`, которым пользовался
  `router.cli.zig`, в установленном Zig **0.16.0** просто не существует —
  это была старая версия API. Разобрали новую модель входа в программу:
  - `main` может объявляться с параметром `init: std.process.Init.Minimal`
    (`struct { environ: Environ, args: Args }`); рантайм (`start.zig:callMain`)
    смотрит на сигнатуру `root.main` через `@typeInfo` и сам подставляет туда
    аргументы/окружение процесса, если такой параметр есть.
  - Сам `Args` — не итератор, а просто носитель platform-специфичного
    `vector`. Итератор получается через `args.iterate()` (`std.process.Args`,
    без аллокатора, на POSIX ок) — и вот у него уже старые знакомые
    `.next()` / `.skip()`.
  - Полный путь типа: `std.process.Args.Iterator`. `std.process.Args` — это
    реэкспорт отдельного файла `std/process/Args.zig`.
  - Это же объясняет, откуда в `main.zig` изначально взялся неиспользуемый
    `const Io = std.Io;` — скаффолд с самого начала целился в эту модель
    входа (`Init`, не `Init.Minimal`, несёт ещё и `.io: Io`), просто до
    подключения дело дошло только сегодня.

- Отдельно споткнулись о `error: expected type '*T', found '*const T'` на
  `router_cli.process(&args)`. Разобрали, что в Zig это не "похожие", а
  **разные** типы указателей, и приведения `*const T → *T` в лоб нет:
  - `&x`, где `x` объявлен через `const` → всегда `*const T`, независимо от
    того, что внутри `T`.
  - `&x`, где `x` объявлен через `var` → `*T`.
  - `Args.Iterator.next()`/`.skip()` мутируют внутреннее состояние
    (продвигают позицию), поэтому и принимают `*T` — значит, и переменная
    `args` перед вызовом должна быть `var`, не `const`. Починили сменой
    объявления, не приведением типов.

- Ещё две мелкие путаницы по ходу дня:
  - `zig build run left` падал с `no step named 'left'` — всё, что идёт
    после `zig build`, парсится как имена шагов/опций build-системы, а не
    как argv программы. Нужен разделитель: `zig build run -- left`
    (`b.args` в `build.zig` заполняется именно из того, что после `--`).
  - "exe" в логах сборки (`compile exe iwwwanow_rubka`) — это не про
    Windows-расширение, а просто внутреннее имя типа шага в build-DSL
    Zig (`b.addExecutable`). На Linux бинарник в `zig-out/bin/` без
    расширения — проверили `file` на реально собранном бинарнике.

## На завтра

Начинаем изучать **sway IPC протокол** — следующий шаг это заменить
`StubWindowManagerAdapter` на `sway.adapter.zig` (файл уже есть в
`src/infrastructure/adapters/`, но пустой/не подключён в `main.zig`).

Договорились на словах (без кода):
- IPC sway — это unix-сокет с простым бинарным фреймингом
  (`i3-ipc` magic + длина + тип + JSON-пейлоад), `swaymsg` — тонкая
  обёртка поверх того же сокета, не единственный способ им пользоваться.
  Можно говорить с сокетом напрямую из Zig, не шеллиться в `swaymsg`
  каждый раз.
- Кроме команд (`RUN_COMMAND` и т.п.) протокол даёт `GET_TREE` (снимок
  всего дерева окон/воркспейсов/аутпутов с id и геометрией) и `SUBSCRIBE`
  на события (`window`, `workspace`, `binding`, ...) — то есть можно не
  дёргать `GET_TREE` поллингом, а держать у себя в памяти зеркало
  состояния и обновлять его по событиям.
- Открытый вопрос "хранить состояние окон в памяти или спускаться на
  уровень Wayland" пока не решён — прикидка (не финал): sway IPC уже
  даёт нужный уровень абстракции с событиями, спуск на raw Wayland
  (`wlr-foreign-toplevel-management` и т.п.) добавляет объём работы без
  явного выигрыша, если цель — управлять именно sway, а не писать
  compositor-независимый тул. Вернуться к этому предметно, когда дойдём
  до кода адаптера.

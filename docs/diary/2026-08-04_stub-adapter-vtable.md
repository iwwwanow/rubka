# 2026-08-04 — заглушка-адаптер и vtable руками

- Обсудили именование заглушки: `stub` vs `console` (терминология test-doubles
  vs имя по поведению). Остановились на `stub` — файл
  `src/infrastructure/adapters/stub.adapter.zig`, структура
  `StubWindowManagerAdapter`, симметрично будущему `sway.adapter.zig`.
- Собирали vtable-обёртку для заглушки пошагово, руками, разобрав по пути
  несколько новых концепций:
  - Пустая структура `struct {}` — валидный тип без полей; нужна только как
    адрес, на который можно "показать" через `*anyopaque`, состояния нет.
  - Метод vs обычная функция внутри структуры: метод — функция, чей первый
    параметр по типу совпадает с тем, что слева от точки (даёт сахар
    `x.foo()`). Функция под сигнатуру `move_fn` в порту обязана первым
    параметром принимать именно `*anyopaque` — точке она не подчиняется,
    это просто функция, лежащая рядом со структурой, не привязанная к ней
    синтаксически.
  - `имя_поля: Тип` разобрали на примере `move_fn: *const fn (ptr: *anyopaque,
    direction: Direction) void` — `fn(...) void` тут тип функции (форма,
    не тело с реализацией), `*const` — указатель на неизменяемый код;
    имена параметров внутри типа — не более чем документация.
  - `@ptrCast` — builtin, выводит целевой тип из контекста использования;
    голое `_ = @ptrCast(ptr);` контекста не даёт ("must have a known result
    type"). Чинится явным типом слева от присваивания:
    `const self: *StubWindowManagerAdapter = @ptrCast(ptr);`.
  - `self`, полученный через `@ptrCast`, у заглушки оказался нечитаемым —
    структура пустая, доставать нечего. Разобрали, что это следствие
    конкретно пустой реализации, а не обязательный ритуал: у будущего
    sway-адаптера (с настоящим сокетом IPC) `self` будет реально нужен для
    чтения состояния. Раз тут не нужен — явно отброшен через `_ = self;`,
    а само приведение оставлено как задел на будущее/консистентность формы
    с настоящими адаптерами, а не убрано вовсе.
  - Литерал структуры `.{ .field = value, ... }` — одно выражение, поля
    через запятую внутри одних скобок, а не последовательность отдельных
    присваиваний. Плюс: в Zig нет неявного возврата последнего выражения
    (в отличие от Rust) — нужен явный `return`. Оба момента сначала сломали
    `wrap` ("invalid left-hand side to assignment"), потом поправили.
  - Поймали недостающий `pub` на `wrap` заранее, по аналогии с разбором
    приватности от 31 июля — до того, как это стало реальной ошибкой сборки
    при обращении из `main.zig`.
- Итог: `stub.adapter.zig` готов — пустая структура, `move_fn`-совместимая
  функция печатает направление через `@tagName`, `pub fn wrap` собирает
  `WindowManagerPort`.
- Начали разбирать сборку composition root в `main.zig`: инстанс
  `StubWindowManagerAdapter` создаётся и живёт в `main.zig` (тип
  импортируется из модуля, но конкретный экземпляр — собственность
  composition root, не модуля), передаётся в `wrap`, дальше оборачивается в
  `MoveWindowUseCase`, потом в `MoveWindowCli`. Разобрали, почему само
  оборачивание в `Port` не должно жить как готовое значение на уровне
  модуля — модуль не должен знать, что именно он выбран для использования
  в конкретном запуске программы, это знание принадлежит только
  composition root.

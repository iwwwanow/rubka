# Менеджмент подключения между устройствами (laptop↔desktop)

Фича: менеджмент подключения между устройствами (laptop↔desktop). Сейчас
вся логика живёт в dotfiles как zsh-функции и отдельный скрипт
(`iwwwanow_dotfiles/.zshrc:58-81`, `iwwwanow_dotfiles/.local/bin/desktop-watch`)
— этот функционал целиком хочется перенести в rubka:

- `desktop()`: ssh-подключение к машине `desktop` с пробросом портов
  (фиксированный 4200 + все текущие docker-порты) и attach/create
  zellij-сессии `main` на удалённой машине
- `desktop-watch`: фоновый процесс поверх `ssh desktop "docker events ..."`
  — на каждый новый контейнер добавляет port-forward в уже открытую
  ControlMaster-сессию (`ssh -O forward`), без реконнекта и без
  перезапуска zellij; убивается вместе с завершением `desktop()`
- `desktop-fwd`: разовый ручной форвард одного порта в уже открытую сессию

Индикация подключения (например в waybar-модуль, по аналогии с
существующими custom-модулями timew/recorder) — обязательная часть,
не опционально.

Соотнести с пунктом "менеджер входа" в [[2026-07-28_modules-idea-list]] —
возможно один и тот же контур ответственности, надо будет решить на
старте сессии проработки.

## Конфигурация и ротация нод

Тот же контур: сегодняшний обрыв `desktop()` (mihomo сломал `tailscaled` на
десктопе, подробности — `iwwwanow_dotfiles/docs/backlog/2026-08-26_ru-node-fallback-for-device-connectivity.md`)
навёл на мысль, что конфигурация путей подключения (Tailscale, SSH
jump-host через РФ-ноду типа `timeweb` как фолбэк в обход mihomo) и ротация
между ними — тоже задача менеджмента подключения между устройствами, а не
что-то отдельное. То есть rubka должна не только держать/индицировать
текущее соединение (`desktop()`/`desktop-watch`), но и знать про несколько
путей и уметь между ними переключаться при отказе основного.
Не проработано — какая нода активна, как определяется отказ, ручное
переключение или авто — вопросы для отдельной сессии.

CLI-интерфейс наметился: `rubka node add` (существительное первым, глагол
вторым — по аналогии с `git remote add`/`docker network create`, дальше под
тот же `node` естественно лягут `node list`/`node remove`/`node switch`).

## Модель node/device и gitops-хранение (обсуждено 2026-08-26)

Предложение: gitops-подход — конфигурация нод и dotfiles живут в одном
git-репозитории (версионируемо, диффуемо), это то же самое хранилище,
которым dotfiles и так является.

- `rubka node add` — подключает ноду, она просто приземляется в
  gitops-сеть для возможности переключаться между устройствами.
- `rubka device add` — подключает девайс (с раскаткой dotfiles + bootstrap).
  Девайс — это тоже нода по сути, просто с надстройкой в виде
  dotfiles + bootstrap: `device add` = `node add` + применение
  dotfiles/bootstrap поверх (композиция, не отдельная сущность).
- оценка подхода: сама композиция node⊂device разумна, gitops-хранение
  тоже вписывается в существующую модель (dotfiles и так git-репо).

Риск, который надо развести явно, прежде чем закреплять CLI: термин
"node" рискует значить две разные вещи одновременно.
- В разделе выше "node" = путь подключения для фолбэка (Tailscale-роут,
  SSH jump-host через `timeweb` в обход mihomo) — то есть **как**
  достучаться до устройства.
- В этом разделе "node" = само устройство, между которыми переключаются
  — то есть **что** подключено.
- Это не одно и то же: у одного устройства может быть несколько путей
  подключения (node в первом смысле), и при этом само устройство может
  быть node-ом во втором смысле, к которому эти пути ведут. Нужно либо
  явно развести два понятия под разными именами (например `route`/`path`
  для путей подключения, `node` только для устройств), либо осознанно
  зафиксировать, что "node" — это общий термин, покрывающий оба смысла,
  и решить как их различать в структуре данных/CLI. Не решено — вопрос
  для отдельной сессии.

## Инициализация/связывание через git — вопрос кредов (открыто, не решено)

Идея: связывание/инициализация всего этого происходит через git — новое
устройство подключается через тот же gitops-репозиторий. Открытые вопросы,
поднятые в обсуждении, пока без ответа:

- какие креды нужны для инициализации нового устройства — предположительно
  SSH-ключ, но не проверено
- совместимость между git-провайдерами: `gh` — CLI-инструмент, который
  берёт на себя авторизацию/API GitHub целиком, но что если конфиги на
  GitLab или Bitbucket? Хочется провайдер-агностичную систему, а не
  завязанную на `gh`/GitHub API.
- достаточно ли прав у голого SSH-ключа (git clone/pull/push) для всего,
  что нужно gitops-контуру, или потребуется ещё platform-specific PAT
  (GitHub PAT / GitLab access token / Bitbucket app password) для чего-то
  сверх git-операций (например API-вызовов, а не просто git-транспорта)?
  Не проработано — нужно сначала определить, что именно rubka будет
  делать помимо голого git clone/pull/push (если ничего — SSH-ключа может
  быть достаточно и провайдер вообще не важен, раз git-транспорт
  везде одинаковый).

Ответ на вопрос выше (зафиксировано 2026-08-26): голого SSH-ключа
достаточно для самого git-транспорта (`git-upload-pack`/`git-receive-pack`
по SSH) — этот протокол одинаковый на GitHub, GitLab, Bitbucket и любом
self-hosted git (Gitea и т.д.), provider-специфики в clone/pull/push нет,
совместимость между провайдерами получается "бесплатно". Единственное
место, где провайдер всё же вылезает — регистрация SSH-ключа нового
устройства у провайдера *до* первого clone (deploy key / ключ в аккаунте):
это разовый bootstrap-шаг, который либо руками через UI, либо через
provider API, а для API уже нужен PAT (GitHub PAT / GitLab access token /
Bitbucket app password) — сам git-протокол способа "зарегистрируй мой
ключ" не даёт. То есть PAT нужен не для повседневной синхронизации, а
только если автоматизировать именно этот bootstrap-шаг под каждый
провайдер отдельно; иначе он остаётся ручным разовым действием.

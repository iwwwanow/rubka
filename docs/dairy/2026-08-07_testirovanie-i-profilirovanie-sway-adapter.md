# 2026-08-07 — Стратегия тестирования и профилирования sway-адаптера

Перед тем как начинать писать `sway.adapter.zig`, обсудили отдельно (без кода) —
чем и как это гонять, чтобы не тестировать руками через рабочую sway-сессию.
Разложили на три независимых слоя, у каждого свой инструмент:

1. **Кодирование/декодирование i3-ipc сообщений — чистый юнит-тест, sway вообще
   не нужен.** Фрейминг (`i3-ipc` magic + длина + тип + JSON-пейлоад) можно
   вынести в отдельные функции, не завязанные на сокет, и гонять `zig test` на
   фиксированных байтовых буферах. Это самая дешёвая и самая частая проверка —
   строить с неё. Держать "сериализация протокола" отдельно от "сокет I/O" —
   то же разделение, что уже есть между портом и адаптером, просто на уровень
   глубже.

2. **Round-trip через реальный сокет — вложенный (nested) sway**, а не рабочая
   сессия:
   ```
   WLR_BACKENDS=wayland sway
   ```
   Второй, независимый compositor в окне текущей графической сессии, со своим
   `$SWAYSOCK`. Бинарник направляется на него через `SWAYSOCK=<путь>`, внутри
   открываются тестовые `foot`-терминалы, `left`/`right` гоняются визуально, а
   сломать нечего, кроме тестового окна. Это основной ручной dev-loop для
   sway-адаптера.

3. **Воспроизводимые/скриптованные прогоны — headless sway**, отложено до
   появления сценариев, которые хочется гонять автоматически/регрессионно
   (баги мастер-стека из `docs/backolg.md`):
   ```
   WLR_BACKENDS=headless sway
   ```
   Без дисплея, чисто процесс с сокетом — можно скриптом спаунить окна и
   прогонять сценарии. Пригодится не сейчас, а когда появится набор
   регрессионных проверок.

**Профилирование**: пока адаптер — короткоживущий CLI (коннект → запрос →
ответ → выход), отдельный сендбокс под это не нужен: `strace -T` / `perf stat`
поверх nested-инстанса достаточно. Отдельное профилирование понадобится
предметно, если дойдём до пункта из `docs/backolg.md` "менеджер окон +
переключение между ними" — то есть когда адаптер станет долгоживущим процессом
с `SUBSCRIBE` и зеркалом состояния в памяти; тогда headless-сендбокс со
скриптованной нагрузкой понадобится уже для профилирования, а не только для
тестов.

**Итог**: юнит-тесты на фрейминг без sway → nested sway как основной ручной
dev-loop → headless отложить до появления сценариев автоматизации. Живой
рабочий sway-инстанс использовать только для финального "потрогать руками",
не как основной цикл разработки.

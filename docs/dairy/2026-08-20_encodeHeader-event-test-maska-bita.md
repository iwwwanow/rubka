# 2026-08-20 — encodeHeader event-тест: где должна стоять маска бита

Продолжение серии 08-17…08-19 про `encodeHeader`. Начали с ревью уже
написанного `encodeHeader: valid message frame` (закрыт полностью — magic,
payload_length, payload_type проверены независимыми оракулами, все три
поля 14-байтного заголовка покрыты), затем перешли к event-тесту.

## Баг в первой версии event-теста

Изначально `| 0x80000000` стоял не на той стороне сравнения:

```zig
const decoded_raw_type = std.mem.readInt(u32, event_frame[...][0..4], endian) | 0x80000000;
try testing.expectEqual(@intFromEnum(header.payload_type.event), decoded_raw_type);
```

`event_frame` — уже результат `encodeHeader`, то есть в байтах бит `event`
(31-й, старший) уже установлен production-кодом. OR поверх уже
установленного бита — no-op, сам по себе не баг. Настоящая проблема —
сравнение шло с *голым* `@intFromEnum(...)` (без бита) вместо ORed-значения,
так что `expectEqual(3, 0x80000003)` падал.

## Разбор: куда должна идти маска

Прожали на конкретных числах (не абстрактно "expected/actual side" — это
не заходило, зашло только через двоичное представление):

- `EventType.window = 3` → `00000000 00000000 00000000 00000011`
- После кодирования event: `10000000 00000000 00000000 00000011` = `0x80000003`
- Это число реально лежит в буфере — читать его нужно **как есть**, без
  масок (`readInt` — и всё).
- `@intFromEnum(header.payload_type.event)` даёт голый `3` — enum
  ничего не знает про флаг event/message, эта информация живёт в теге
  union, не в самом числе.
- Значит `| 0x80000000` — это ручная сборка *предсказания* с нуля из
  голой цифры, а не операция над прочитанными байтами.

Финальный рабочий вариант:

```zig
const decoded_raw_type = std.mem.readInt(u32, event_frame[...][0..4], endian);
try testing.expectEqual(@intFromEnum(header.payload_type.event) | 0x80000000, decoded_raw_type);
```

Также разобрали (и отвергли) альтернативный "неправильный, но тоже
зелёный" вариант — замаскировать `decoded_raw_type` через `& 0x7FFFFFFF`
и сравнивать с голым enum-значением без OR. Формально тоже проходит, но
убивает смысл теста: если `encodeHeader` забудет поставить бит для
event-ветки (тот самый баг из 08-17, ради которого весь этот тест и
задуман), `& 0x7FFFFFFF` над уже-безбитным числом ничего не меняет —
тест не заметит регрессию. Правило: **маскировать/дополнять можно только
предсказание (то, что вычисляешь сам из чистого enum), но не то, что
реально прочитано из буфера** — иначе тест перестаёт быть независимой
проверкой.

## Общее правило OR vs AND (для памяти на будущее)

- `|` (OR) — **устанавливает** бит. Используется когда *собираешь*
  значение с нуля (кодирование, или ручная сборка ожидания в тесте).
- `&` (AND) — **читает/убирает** бит. Используется когда *разбираешь*
  уже готовое значение (декодирование: `is_event = raw & 0x80000000`,
  `masked_type = raw & 0x7FFFFFFF`).

Паттерн "флаг в старшем бите + значение в остальных" — общий, встретится
ещё не раз (unix-права, HTTP/TCP-флаги, errno и т.д.), не разовая
специфика i3-ipc.

`encodeHeader: valid event frame` — исправлен и закоммичен
(`d8917c9 feat(infrastructure): sway event test`). Оба `encodeHeader`-теста

## payload_length граничные значения — оказалось не совсем "границы"

Взялись за кандидата №1 (0 и `maxInt(u32)`). По пути выяснилось: тест на
самом деле не проверяет границы диапазона в смысле "могло бы сломаться на
краях". Причина — `encodeHeader` вообще не видит payload (принимает только
`Header`, без байт тела), так что не может проверить согласованность
`payload_length` с реальными данными — это ответственность более высокого
уровня (будущий полный encode).

А внутри самого `encodeHeader` для `payload_length` нет ветвления по
значению: `writeInt(u32, ..., value, endian)` при совпадающих
size/endian эквивалентен `memcpy`, поэтому `expectEqualSlices(u8,
std.mem.asBytes(&header.payload_length), frame[...])` пройдёт для
**любого** `u32`, не только 0 и `maxInt` — код не различает "маленькое" и
"большое" число. Плюс сам тип `u32` физически не пропустит значение вне
`[0, maxInt(u32)]`, так что классического overflow/underflow тут просто
неоткуда взяться.

Вывод: реальная польза этих двух тестов — не "ловит баг на границе", а
**regression guard**: если в будущем в `encodeHeader` добавится
валидация/клэмпинг `payload_length`, тест сломается и явно покажет смену
контракта. Написаны как `encodeHeader: payload_length zero` и
`encodeHeader: payload_length zero u32` (см. ниже про опечатку в имени),
с комментарием `// INFO: regression guard` над каждым.

**Опечатка**: второй тест (для `maxInt(u32)`) назван `"payload_length zero
u32"` — скопировано с первого и не поправлено на `max`. Поправить в
следующей сессии перед коммитом.

Комментарий-кандидат №3 в хвосте `sway.adapter.test.zig` (строка про
"payload_length — граничные значения") теперь устарел — тесты под ним уже
написаны, комментарий не убран.

   Проверить, что `encodeHeader` кодирует произвольное значение (например
   `9999`) как есть, не падает/не обрезает. В отличие от
   `payload_length`-теста — здесь реальная логика через `switch` на
   `payload_type`, есть что ловить.
3. **Round-trip тест** (`decodeHeader(&encodeHeader(header))`) — с
   оговоркой из 08-19, что он дополняет, но не заменяет тесты с явно
   прописанными байтами (не поймает симметричный баг в обеих функциях).

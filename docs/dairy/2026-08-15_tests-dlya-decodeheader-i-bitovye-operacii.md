На входе — один тест на `decodeHeader` (message frame, happy path).
`FrameError` объявляет два варианта (`InvalidMagic`, `BufferTooShort`),

## `expectError`, а не `try`

Первая версия теста на `BufferTooShort` была `try adapter_mod.decodeHeader(...)`
без сравнения — это не проверка ошибки, а её проброс: `try` просто
завалит тест при любой ошибке, не сверяя, какая именно. Правильный
инструмент — `std.testing.expectError(expected_error, actual_error_union)`,
причём второй аргумент передаётся **без** `try`/`catch` — `expectError`
сам разворачивает error union и сравнивает.

## Находка: build-граф "5/5 steps" не отражает число тестов

После добавления теста на `BufferTooShort` `zig build test --summary all`
показывал всё то же "5/5 steps succeeded", что и вчера — возникло
подозрение, что тест не считается. Разобрались: "5/5" — это узлы
build-графа (`test` → 2×`run test` → 2×`compile test`, из `mod_tests`/
`exe_tests`), а не количество `test {}` блоков. Один `compile test` шаг
компилирует весь тестовый бинарник целиком, сколько бы тестов внутри ни
было — граф в принципе не даёт такой гранулярности.

Проверили гипотезу через намеренную поломку теста (буфер `header_length`
вместо `header_length - 1`, что должно было дать `InvalidMagic` вместо
ожидаемого `BufferTooShort` — мисматч, тест обязан упасть). Не упал.
Сначала заподозрили `.zig-cache` — `rm -rf .zig-cache` и пересборка с
нуля (`compile test ... success`, не `cached`) не изменили результат.
Кеш был ни при чём.

### Реальная причина: файл не входит в граф анализа для обоих тестовых бинарников

`test {}` блоки из импортированного файла подхватываются в тестовый
бинарник, только если контейнер этого файла реально анализируется
компилятором — просто `const x = @import("...")`, которое нигде не
используется, анализ не форсирует. В `sway.adapter.zig` уже есть
идиома под это:

```zig
test {
    _ = @import("sway.adapter.test.zig");
}
```

Но та же проблема повторялась на уровень выше: `root.zig` (корень
`mod_tests`) вообще не импортирует `sway.adapter.zig`; `main.zig`
(корень `exe_tests`) импортирует, но `sway_adapter_mod` нигде не
использовался — значит анализ контейнера `sway.adapter.zig` не
форсировался ни там, ни там. Вывод: **ни один тест из
`sway.adapter.test.zig` реально не запускался** ни разу, включая
вчерашний happy path — зелёный "5/5" был лживым для этого файла с
самого начала.

Починили временно (вариант "оба файла", без переноса в `root.zig`):
в `main.zig` добавлен

```zig
test {
    _ = @import("./infrastructure/adapters/sway.adapter.zig");
}
```

с комментарием `// TODO: refactor; mv test imports to root zig` — это
чинит только `exe_tests`; `mod_tests` (`root.zig`) по-прежнему не видит
эти тесты, но `root.zig` сейчас leftover-заглушка от `zig init`
(только `printHelloWorld`), так что решили не блокироваться на этом.
Отдельно обсудили архитектурный вариант B (нормальный, не временный):
экспонировать `sway.adapter.zig` через `root.zig` как часть публичного
модуля пакета, раз `main.zig` — это composition root, а не место для
тестового wiring. Не сделано сегодня, TODO-комментарий в коде указывает
на это, но пункт в `docs/backolg.md` ещё не зафиксирован явно — сделать

## Тест на event-ветку поймал ещё один баг — уже в самом тесте

Первая версия `"decodeHeader: valid event frame"` писала в
`payload_raw_type` просто `@intFromEnum(constants_mod.EventType.window)`
(`= 3`), без установки старшего бита. Результат — паника рантайма:

```
access of union field 'event' while field 'message' is active
```

Причина: `decodeHeader` решает event/message по биту 31
(`payload_raw_type & 0x80000000 != 0`) — без него `masked_type = 3`
интерпретируется как `MessageType.get_outputs`, не как event. Тест
собирал невалидный (с точки зрения реального протокола) фрейм: в
`sway-ipc` бит 31 — это флаг "это событие, а не ответ на команду",
из-за него в `decodeHeader` вообще есть маскирование (TODO "dont
understand it" на `sway.adapter.zig:37` — теперь понятно, что там).

Исправление: `@intFromEnum(constants_mod.EventType.window) | 0x80000000`.

## Битовые операции: AND vs OR, откуда берётся 1 в 0x80000000

Ушли в сторону от кода — разобрали механику на пальцах, стоило того:

- `&` (AND) — извлечение/обнуление битов, `|` (OR) — установка битов.
  Не путать с булевыми `and`/`or` в Zig — те работают только с `bool`
  целиком, `&`/`|` — побитово на `u32`.
- `&`/`|` **идемпотентны**, не самообратимы: применить `| mask` дважды
  — то же самое, что один раз, "отменить" через повторный `|` нельзя.
  Самообратим только XOR (`x ^ mask ^ mask == x`) — переключает биты
  туда-обратно. Чтобы снять бит, поставленный через `|`, нужен `&` с
  инвертированной маской (`x & ~mask` / `x & 0x7FFFFFFF` — как раз то,
  что делает `decodeHeader` для чтения типа).
- Почему в `0x80000000` "восьмёрка", а бит один: один hex-символ = 4
  бита. Hex-цифра `8` = `1000` в двоичном (не "восемь единиц"). Число
  `0x80000000` — 8 hex-символов = 32 бита = `1000 0000 ... 0000`, то
  есть установлен только самый старший (31-й, считая с нуля) бит.
- Разобрали руками столбиком `3 | 0x80000000 = 0x80000003` — ровно то
  значение, что теперь пишет тест.

Договорились: это применение булевой алгебры параллельно к каждой из
32 позиций числа (AND/OR/XOR/NOT — те же таблицы истинности, что и в
обычной булевой алгебре, просто "столбиком" по битам). Стоит порешать
руками отдельно от кода: hex↔binary на глаз, таблицы истинности,
set/clear/toggle бита через `|`/`&~`/`^`, и отдельно — почему
`& 0x7FFFFFFF` в `decodeHeader` стирает именно верхний бит. Наметили
формат для практики в дороге (без ноутбука/тетради): programmer mode
в калькуляторе на телефоне как "оракул" для проверки (сначала
предсказать в уме, потом сверить), плюс Anki-колода на hex-ниблы и
таблицы истинности для доведения до автоматизма.

## Roadmap после decodeHeader: обсудили порядок дальнейшей работы

Не код, только план на следующие сессии, зафиксировали порядок и где
что должно жить.

- **Разбор payload** — JSON-тело фрейма после заголовка (`std.json`),
  сейчас код его вообще не трогает, есть только `payload_length`/
  `payload_type`.
- **encode — следующий шаг, с него начнём следующую сессию.** Симметрично
  `decodeHeader`, но в другую сторону: собрать исходящий фрейм
  (magic + length + type + JSON payload) для отправки команд
  (`run_command`). Важно: `encode` — чистая функция, ничего не пишет
  сама, не знает про сокет — просто отдаёт байты фрейма. Кто эти байты
  реально отправляет (в сокет, в тестовый буфер) — забота вызывающего
  кода, не `encode`. Тесты на `encode` планируем сразу вместе с
  реализацией, по аналогии с тем, как делали decode.
- **Socket I/O** — отдельный слой поверх encode/decode, нужны и запись
  (отправка команд), и чтение (ответы + event-фреймы от `subscribe`).
  Про тестирование этого слоя обсудили два варианта, не выбрали пока:
  (а) абстрагировать сокет за интерфейсом (`std.io.Reader`/`Writer`
  или свой vtable-порт по аналогии с `WindowManagerPort`) и тестировать
  на in-memory буферах; (б) реальный `std.posix.socketpair` в тесте —
  честнее, но тяжелее писать. Вероятно нужны оба уровня (unit на
  abstracted reader/writer + пара integration-тестов на реальном
  socketpair), но решать по факту, когда дойдём.
- **Методы `WindowManagerPort`** (сейчас только `move(direction)`) —
  после encode/socket это просто оркестрация: собрать JSON-команду →
  `encode` → write → read ответа → `decodeHeader` + разбор payload на
  успех/ошибку. Ничего протокольно нового, вся сложность уже будет
  закрыта на предыдущих шагах. Порт на vtable-паттерне (`ptr` +
  `*const fn`) легко расширяется дальше — `get_tree`/`subscribe` из
  исходного скоупа добавятся так же, ещё одним указателем на функцию,
  переиспользуя тот же протокольный слой.
- Оценка объёма: encode + socket — видимо самая большая оставшаяся
  часть низкоуровневой работы (decode готов, payload — умеренно,
  методы порта — тонкая склейка).
- **Расположение вспомогательных функций**: решили, что общий `util/`
  не заводим — держим scoped к адаптеру внутри `infrastructure/`, по
  той же схеме именования, что уже есть (`sway.adapter.constants.zig`,
  `sway.adapter.test.zig`) — что-то вроде `sway.adapter.frame.zig` для
  encode/decode вместе. Причина: это протокольная механика конкретно
  sway-ipc, не общего назначения; если позже появится переиспользование
  за пределами sway (например, для будущего GNOME-адаптера из
  бэклога), тогда стоит пересмотреть.

# 2026-08-17 — encodeHeader: реализация и ревью

Продолжение сессии от 08-15: начали `encode` для исходящих фреймов,
как и планировали, с `encodeHeader` — заголовочной части, симметричной
`decodeHeader`.

## Ход обсуждения перед кодом

- Подтвердили сигнатуру: `encodeHeader(header: Header) [constants_mod.header_length]u8`.
  Fixed-size array, а не слайс — размер заголовка известен на этапе
  компиляции, аллокатор не нужен, отражает "чистую функцию" из плана
  08-15.
- Разобрали асимметрию decode/encode: `decodeHeader` принимает
  `buf: []const u8` произвольной длины, потому что читает внешние,
  неконтролируемые данные (частичное чтение из сокета, payload после
  заголовка в том же буфере) — отсюда `BufferTooShort`. `encodeHeader`
  сам производит байты фиксированного протокольного размера, поэтому
  может вернуть строго `[header_length]u8`.
- Первая версия encode содержала баг: `@intFromEnum(header.payload_type)`
  на tagged union возвращает индекс **тега** union'а (0/1 по порядку
  объявления `message`/`event`), а не значение `MessageType`/`EventType`
  внутри варианта. Плюс безусловный `| 0x80000000` ставил event-бит
  даже для message-фреймов. Исправили через `switch` с capture:

  ```zig
  const payload_raw_type: u32 = switch (header.payload_type) {
      .message => |m| @intFromEnum(m),
      .event => |e| @intFromEnum(e) | 0x80000000,
  };
  ```

- Обсудили `switch` vs `if`: decode работает над сырыми битами (`if`
  уместен для проверки одного бита), encode — над уже типизированным
  tagged union, где `switch` с capture (`|m|`/`|e|`) — идиоматичный
  способ безопасно достать payload варианта. Zig не поддерживает `==`
  напрямую на union, так что `if` здесь потребовал бы
  `std.meta.activeTag` и менее безопасный ручной доступ к полю —
  решили, что "зеркальность" decode/encode не обязана означать
  одинаковый синтаксис, раз домены разные (биты vs типизированные данные).
- `endian` подняли с уровня функции на уровень модуля — используется
  в обеих функциях (`decodeHeader` и `encodeHeader`), дублирование не
  нужно.

## Ревью финального диффа

Диф: `src/infrastructure/adapters/sway.adapter.zig` (+23 строки,
`encodeHeader` целиком) и `sway.adapter.test.zig` (2 строки — убраны
пустые строки, шум без функциональных изменений).

**Что хорошо:**
- Логика верна: magic копируется константой, `payload_length` и
  `payload_raw_type` пишутся тем же `std.mem.writeInt` с тем же
  `endian`, что и чтение в `decodeHeader` — порядок байт симметричен.
- `header_buf` объявлен `undefined`, но все 14 байт (6 magic + 4 length
  + 4 type) гарантированно перезаписываются (`@memcpy` + два
  `writeInt`) до `return` — никакого непроинициализированного мусора
  наружу не уходит.
- `switch` с capture корректно разворачивает tagged union в обе
  стороны (`message`/`event`), правильно преобразует в `u32` и ставит
  event-бит только для `event`-ветки — тот самый баг из черновика
  устранён.
- Возврат `[constants_mod.header_length]u8` вместо `[14]u8` — нет
  магического числа, тип автоматически согласован с константами.
- Вынос `endian` на уровень модуля — правильное место, раз используется
  в обеих функциях; вычисляется на этапе компиляции (`builtin.cpu.arch`
  comptime-известен), так что просто убирает дублирование, не влияет
  на рантайм.

**Чего не хватает (перед тем, как считать шаг закрытым):**
- **Тестов на `encodeHeader` нет.** В плане от 08-15 явно было
  "тесты на encode планируем сразу вместе с реализацией, по аналогии с
  decode" — это ещё не сделано, реализация пока непроверена
  автоматически. Нужно минимум: happy path для `message`, happy path
  для `event` (чтобы отдельно проверить установку старшего бита),
  и, вероятно, round-trip тест (`decodeHeader(&encodeHeader(header))
  == header`, с учётом что decode ожидает payload после заголовка —
  либо тестировать только сам 14-байтный префикс).
- У `encodeHeader` в принципе нет error-путей (в отличие от decode) —
  на входе уже валидный `Header` из типизированных полей Zig, так что
  это не пропущенный кейс, а следствие дизайна: невалидные состояния
  (например, `payload_raw_type` вне известных тегов) на входе encode
  просто непредставимы, раз `MessageType`/`EventType` — non-exhaustive
  enum и `PayloadType` требует одного из двух конкретных вариантов.
  Стоит просто держать это в уме как асимметрию с decode, а не как
  недоделку.

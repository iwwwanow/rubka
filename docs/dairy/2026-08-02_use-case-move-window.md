# 2026-08-02 — use-case move-window, приватность и naming

- Написали `MoveWindowUseCase` (`src/application/use-cases/move-window.use-case.zig`)
  по аналогии с `draft.ts` — поле `windowManager: Port` по значению +
  метод `execute`, который делегирует в `windowManager.move(direction)`.
  Разобрали, почему use-case **не** нужен собственный vtable (`ptr`/`execFn`),
  в отличие от порта: vtable оправдан только там, где набор реализаций
  открыт и подключается в рантайме (Sway/Hyprland/мок), а `MoveWindowUseCase`
  — конкретный, единственный класс бизнес-логики, который сам *использует*
  подменяемый порт, но не обязан быть подменяемым.
- По ходу нашли и поправили баг в черновике: `self.windowManager.move(.direction)`
  — `.direction` компилятор читает как enum-literal (тег с именем `direction`),
  которого нет в `Direction { left, right }`. Нужно было просто передать
  параметр `direction` без точки.
- Разобрали `pub`-приватность подробнее — ключевая поправка неверной интуиции
  "экспортировал структуру → экспортировались и её методы":
  - `pub` не каскадируется от контейнера на его члены, это свойство каждой
    декларации по отдельности.
  - **Поля** структуры (`ptr: *anyopaque,`, кончаются запятой) вообще не
    берут `pub` — синтаксис не позволяет. Поле видно ровно настолько,
    насколько виден сам тип.
  - **Декларации** внутри struct (`fn`, вложенные `const`/`var`, через `=`)
    — это отдельный namespace, вложенный в namespace файла, со своей
    независимой по-файлу-приватностью. Поэтому `fn move(...)` и
    `Direction` пришлось помечать `pub` отдельно от самой структуры.
- Ещё раз подробно разобрали метод-сахар (`x.foo(args)`): если тип `x` — `T`,
  и в namespace `T` есть `fn foo(self: T | *T | *const T, ...)`, компилятор
  переписывает вызов в `T.foo(x, args)`. Имя первого параметра (`self`) —
  чистая конвенция, не keyword; решает только тип по позиции. Работает в
  обе стороны с указателями (авто `&x` / авто-разыменование). Отдельно
  отметили, что это чисто compile-time синтаксическая переписка, не имеющая
  отношения к рантайм-диспетчингу vtable из `Port` — два независимых
  механизма. И что `self.moveFn(...)` внутри `move` — **не** этот сахар:
  `moveFn` поле, а не декларация, там просто field access + вызов
  значения-указателя, синтаксически похоже, механизм другой.
- Naming/style по официальному Zig style guide: файл, который **есть тип**
  (корень файла = сама сущность) → `TitleCase.zig` + прямой импорт типа
  (`const Allocator = std.mem.Allocator;`). Файл-**неймспейс** (россыпь
  связанных деклараций) → `snake_case`-имя при импорте + доступ через точку,
  как `std`. `window-manager.port.zig` экспортирует две вещи (`Direction` +
  `Port`) — второй случай. Заменили два раздельных `@import` на один
  `const window_manager_port = @import(...)`, и заодно переименовали
  `WindowManagerPort` → `Port` — при доступе через namespace старое имя
  давало stutter (`window_manager_port.WindowManagerPort`), паттерн решения
  тот же, что `std.mem.Allocator`, а не `std.mem.MemAllocator`.
- Отдельно закрепили: конвенция camelCase/snake_case смотрит на **форму
  объявления** (`fn`-декларация vs поле/переменная), а не на тип значения.
  `moveFn`/`windowManager` — поля, значит snake_case (`move_fn`,
  `window_manager`), даже при том что `moveFn` хранит указатель на функцию —
  это деталь его типа, а не форма объявления самого поля.

`Port` (см. вчерашний разбор паттерна). Обновить `docs/diagram.d2` под

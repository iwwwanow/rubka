# 2026-08-10 — MessageType, нейминг констант и план на decodeHeader

Продолжение сессии от 08-08: закрыли открытый вопрос exhaustive/non-exhaustive
и перенесли обе таблицы (`MessageType`, `EventType`) из man-страницы в код.

## Решение: non-exhaustive enum

Выбрали non-exhaustive (висящий `_,` в конце списка тегов) для обоих enum'ов.
Причина: списки в `man 7 sway-ipc` не плотные диапазоны, а "известные на
сегодня" теги (разрыв 12→100 у `MessageType`, 7→20 у `EventType`) — новые
версии sway со временем добавляют значения сверх этого списка. Non-exhaustive
означает, что `decodeHeader` не должен падать на незнакомом `payload_type` —
это станет заботой кода выше (use-case/application), который уже понимает,
нужен ли ему конкретный тип, а не заботой фрейминга.

## Код: вынос констант в отдельный файл

`MessageType`/`EventType` заполнены полными таблицами и вынесены из
`sway.adapter.zig` в новый `sway.adapter.constants.zig`:

```
src/infrastructure/adapters/sway.adapter.constants.zig
  pub const MessageType = enum(u32) { run_command = 0, ..., get_seats = 101, _ };
  pub const EventType   = enum(u32) { workspace = 0, ..., input = 21, _ };
```

`sway.adapter.zig` теперь импортирует их как `constants_mod` и ссылается из
`PayloadType`. `/code-review` по этому диффу — без находок: значения enum'ов
сверены с man-страницей на этой машине и совпадают, рефакторинг чистый,
нейминг соответствует правилу из `CLAUDE.md`.

## Zig-заметки за сессию: нейминг, а не только синтаксис

- Теги enum — `snake_case`, а не `CAPS`, как в самой man-странице
  (`BAR_STATE_UPDATE` → `bar_state_update`). Правило из `CLAUDE.md` про
  консистентность с терминологией спеки — про смысл имени (`payload_length`,
  а не `length`), не про регистр букв. Регистр — отдельная ось, задаётся
  Zig style guide: `TitleCase` только для типов, всё остальное
  (переменные, поля, значения enum) — `snake_case`.
- Отсюда же: строковые константы в Zig тоже `snake_case`
  (`const magic = "i3-ipc";`), не `CAPS`, в отличие от привычки из TS/JS.
  Причина разницы — в TS `const` слабая гарантия (не защищает от мутации
  значения, только от переприсваивания имени), поэтому `CAPS` там —
  дополнительный визуальный сигнал "это настоящая неизменяемая константа".
  В Zig `const` — сильная гарантия на уровне языка, регистр не нужен как
  костыль для той же информации.
- Как физически хранится строковый литерал: `"i3-ipc"` имеет тип
  `*const [6:0]u8` — указатель на sentinel-terminated массив известной на
  этапе компиляции длины, лежит в read-only секции бинарника. При передаче
  туда, где ожидается `[]const u8`, происходит неявный coercion
  (указатель-на-массив → слайс), поэтому `std.mem.eql(u8, buf[0..6],
  "i3-ipc")` компилируется без явных преобразований.
- Non-exhaustive enum на практике: `std.meta.intToEnum`/`@enumFromInt` на
  таком enum никогда не паникуют и не возвращают ошибку — любое значение
  integer-типа валидно. Обратная сторона — `switch` по такому enum
  **обязан** иметь ветку `else` (компилятор не может доказать полный
  перебор), и незнакомый тег туда и попадёт.

## Открытый вопрос, разобранный к следующей сессии

Уточнили, где именно будет жить разбор `payload_type` при декодировании.
Важное разграничение:

- Собрать `PayloadType` из сырого `raw_type` — это **не switch**, а
  `if`/маска: проверка старшего бита (`raw_type & 0x80000000 != 0`) решает,
  в какую из двух веток union'а (`.message`/`.event`) класть значение, а
  само значение получается через `@enumFromInt`/`intToEnum` на
  замаскированном числе (`raw_type & 0x7FFFFFFF`). Это происходит внутри
  `decodeHeader` — но это if, не switch.
- `switch` (с обязательным `else` из-за non-exhaustive) появится там, где
  кто-то **реагирует** на конкретные значения `PayloadType`
  (`.workspace`, `.window`, `GET_VERSION` и т.д.) — то есть в
  use-case/application слое, который уже потребляет `Header` от адаптера.
  Внутрь `decodeHeader` такой switch не входит — это чужая забота, адаптер
  только строит типизированное значение и возвращает его.

## Обсуждённые концепции

**Аллокатор** — не отдельный класс, а интерфейс (vtable-паттерн, как уже
есть в `WindowManagerPort`: `ptr` + функции-указатели). `ArenaAllocator` —
не источник памяти сам по себе, а *обёртка над другим (child) аллокатором*:
все реальные alloc-запросы уходят в child, арена просто копит список
аллокаций и освобождает их разом через `arena.deinit()`. Размер не
фиксирован — растёт, пока хватает child'а. Фиксированный буфер — это
отдельный инструмент, `FixedBufferAllocator`, не арена.

Кандидат на child для арены в нашем случае: `GeneralPurposeAllocator` (ловит
утечки в debug) — арена вокруг него на время одного цикла запрос→ответ по
сокету. Не финализировано, вернуться при проектировании сигнатуры
`encode`/`decode`.

`std.ArrayList(u8)` — освобождение не автоматическое (в Zig нет RAII),
`.deinit()` вызывается вручную, идиома — `defer list.deinit()` сразу после
создания (сработает на любом пути выхода из функции).

**Форма JSON в i3-ipc — таблица по типам сообщений:**

| направление | тип | тело |
|---|---|---|
| запрос | `run_command` | **не JSON** — сырая строка, `"move left"` |
| ответ | на `run_command` | `[{"success": true}]` / `[{"success": false, "error": "..."}]` |
| запрос | `subscribe` | `["window", "workspace"]` |
| ответ | на `subscribe` | `{"success": true}` |
| запрос | `get_tree` и т.п. | пусто |
| ответ | на `get_tree` | вложенное рекурсивное дерево нод |
| событие | `window` и т.п. | `{"change": "focus", "container": {...}}` |

Важный вывод сессии: **`run_command`-запрос (то, что реально нужно
`move-window`) — это вообще не JSON, а сырая строка.** То есть минимальный
путь к рабочему end-to-end `move-window` через сокет технически не требует
`std.json` вовсе — нужен только полный `encode` (header + сырые байты
строки). `std.json` становится обязательным, только если: (а) хотим читать
ответ `run_command` (`success`/`error`) для надёжности, или (б) идём дальше
к `subscribe`/событиям (что и так в скоупе `initial-prompt.md`).

**Encode vs decode** — decode не опционален "на потом", он в скоупе
изначально (`subscribe` на `window::new/focus/close` без чтения событий
бессмысленен). Но для голого `move-window` можно обойтись без него
(fire-and-forget).

## Решение по скоупу

Закрываем ровно то, что нужно под `move-window` (use case), генерализуем
механизм encode/decode только когда он реально понадобится под следующий
use case — не проектируем схемы под гипотетическое будущее заранее.
Обоснование сложности `get_tree` (зафиксировано отдельно, чтобы не
удивляться потом): API вызова (`parseFromSlice(T, ...)`) тривиален что для
простого объекта, что для дерева — вся сложность переезжает в
моделирование самой схемы (рекурсивный тип, ~30 полей, опциональность),
не в код.

**Канонический референс** — `man 7 sway-ipc`, не оригинальный i3: тул
подключается к живому sway-сокету (Wayland), а sway уже разошёлся с i3 в
протоколе (`get_inputs`/`get_seats`/`input`-событие — Wayland/wlroots
понятия, которых в i3 нет). i3-докс описывали бы не тот протокол.
Обратная совместимость sway — аддитивная (новые поля добавляются, старые
не ломаются), не "схема заморожена" — отсюда `ignore_unknown_fields` как
паттерн на будущее.

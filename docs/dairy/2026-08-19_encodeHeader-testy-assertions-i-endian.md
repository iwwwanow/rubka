# 2026-08-19 — encodeHeader: assertions, expectEqualSlices, эндианность

Продолжение сессии 08-18: там остановились на том, что конструирование
`Header` в тестах `encodeHeader` синтаксически верно, но сами тесты ещё
пустые — не было ни вызова `encodeHeader`, ни assertions. Сегодня
дописывали тело `encodeHeader: valid message frame`.

## Ход сессии

Шли через несколько неверных итераций, каждая вскрывала свою ошибку:

- **`expectEqual` на срезах/массивах** — первая попытка сравнить magic
  через `expectEqual` не годится: для `message_frame[0..payload_magic_size]`
  (указатель на массив без sentinel) и `i3_ipc_magic` (указатель на
  массив со sentinel, как у любого строкового литерала) типы не
  совпадают и не приводятся друг к другу автоматически; а даже если бы
  совпали — `expectEqual` на указателях сравнивает адрес, а не
  содержимое. Нужен `expectEqualSlices`.
- **Порядок аргументов `expectEqualSlices(T, expected, actual)`** —
  несколько раз путали местами (реальный результат vs ожидаемое
  значение). Функционально не критично (равенство симметрично), но
  портит читаемость сообщения об ошибке при провале теста.
- **Перепутанные офсеты** — при проверке `payload_length` по ошибке
  использовался `payload_raw_type_offset` вместо `payload_length_offset`
  (комментарий в коде говорил "payload length", офсет указывал на
  третье поле).
- **Числа vs байты** — попытка сравнить срез байт с голым числом
  (`example_json.len`, `usize`) через `expectEqualSlices` — несовместимые
  типы. Разобрали два легитимных пути:
  1. `std.mem.readInt(u32, buf_slice, endian)` → сравнить как число
     через `expectEqual` (симметрично тому, что уже делают
     `decodeHeader`-тесты).
  2. `std.mem.asBytes(&value)` → получить срез байт самого значения
     (в нативной эндианности платформы) и сравнить `expectEqualSlices`.
- **Проверка длины буфера как самоцель** —
  `expectEqualSlices(u8, header_length, message_frame.len)` — отдельно
  разобрали, что это не только неверные типы (оба аргумента — числа, не
  срезы), но и тавтология: `message_frame.len` фиксирован типом
  массива (`[header_length]u8`) на этапе объявления, тест ничего не
  проверяет про поведение `encodeHeader`.
- **Payload после заголовка** — по инерции скопированная из
  `decodeHeader`-теста строка, сравнивающая `message_frame[header_length..]`
  с `example_json`, оказалась бессмысленной для `encodeHeader`: функция
  возвращает ровно `[header_length]u8`, без payload — убрали.
- **`asBytes(&header.payload_type.message)` — ловушка со старшим
  битом.** Разобрали отдельно: технически типы совпадают (`MessageType`
  — `enum(u32)`, 4 байта), но семантически неверно для event-кейса —
  `encodeHeader` для event делает `@intFromEnum(e) | 0x80000000`, а
  `asBytes` на union-поле берёт сырую память *до* этой трансформации.
  Такой тест не поймал бы регрессию с забытым битом (тот самый баг с
  08-17). Для message-ветки совпадает случайно (там OR не нужен), но
  подход концептуально хрупкий — тестирует то же преобразование, что и
  продакшн-код, а не независимый оракул.
- **`@intFromEnum(header.payload_type.message)` — итоговый рабочий
  вариант** для message-теста: значение берётся из уже явно
  сконструированного `header` (то же самое, что литерал
  `MessageType.get_version`, просто без дублирования), без прохождения
  через enum-to-bytes память — это `readInt`-совместимое сравнение
  чисел, не байтов. Для event эта же схема потребует явного `| 0x80000000`
  на стороне ожидаемого значения — это ещё предстоит сделать.

## Побочные концептуальные темы (стоит зафиксировать, чтобы не объяснять заново)

- **`@intFromEnum` vs `std.mem.readInt`** — не аналоги. `@intFromEnum`
  работает "значение → значение" внутри системы типов Zig (эндианность
  не участвует, потому что нет сырой памяти для интерпретации).
  `readInt` работает "байты → значение" — пересекает границу между
  плоской памятью и типизированным числом, поэтому и требует `endian`.
- **Round-trip / симметричный баг** — общая тема, всплывавшая дважды
  (сначала с `endian`-переменной, общей для `encodeHeader`/`readInt` в
  тесте; потом с `asBytes` на union-поле): если "ожидаемое" значение в
  тесте вычисляется той же логикой/переменной, что и код под тестом,
  тест перестаёт быть независимой проверкой. Особенно критично для
  старшего бита события — там именно эта развилка когда-то давала
  реальный баг.
- **Байты vs типы, где проходит граница** — отдельный вопрос "все
  данные — это сырые байты?". Ответ: физически память — да, просто
  байты, но внутри одной Zig-программы типы гарантирует компилятор, и
  явно возиться с байтами (и эндианностью) нужно только на границе с
  чем-то, что не разделяет систему типов программы — файл, сокет,
  другой процесс (ровно кейс sway: связь через Unix-сокет с
  C-процессом, отсюда и i3-ipc протокол как контракт интерпретации
  байт).
- **Идея с утилитами-геттерами** — пользователь предложил вынести
  повторяющееся `buf[offset..][0..size]` в хелперы (`getPayloadLengthFromBuf`
  или обёртку `I3ipcBuf`). Обсудили, но не решили окончательно:
  - если хелпер будет переиспользован и в `decodeHeader`, и в тестах на
    `encodeHeader` — это отчасти пересоздаёт проблему round-trip'а
    (тест начинает полагаться на внутреннюю логику декодера);
    формулу ожидания для события (OR-бит) в любом случае стоит держать
    явной в тесте, не прятать в хелпер;
  - при трёх полях в заголовке отдельный геттер на каждое поле —
    вероятно, избыточная абстракция; если делать — один параметризованный
    хелпер (offset, size, endian) → readInt, а не по имени на поле;
  - открытый вопрос пользователю: хелпер нужен только тестам (тогда
    живёт в тестовом файле, не экспортируется) или и продакшену
    (тогда это отдельная рефакторинг-задача для `decodeHeader`,
    не сегодняшняя)?

## Где остановились

`encodeHeader: valid message frame` — тело дописано: проверка magic
(`expectEqualSlices`), `payload_length` (через `asBytes`), `payload_type`
